1. Object representation and undefined behavior

Every serious low-level interview should make you comfortable with the difference between:

  • what the source code appears to mean;
  • what the C/C++ language guarantees;
  • what a particular compiler happens to generate;
  • what a particular CPU happens to do.

Never confuse “it worked on my machine” with “the program is defined.”

int a[4] = {1,2,3,4};
int *p = a;
printf("%d\n", *(p + 2));   // defined: a[2]

int *q = a + 4;
// *q is NOT a valid element access.
// q may be used as a one-past-the-end pointer for comparisons,
// but it must not be dereferenced.

Exercise 8.1

What exactly is wrong with int x[4]; printf("%d", x[4]);? Why is it more serious than “you get garbage”?

x[4] is outside the array. The program has undefined behavior. Once UB occurs, the language imposes no requirements on the result; the compiler is allowed to make transformations based on the assumption that valid programs do not perform that access. Therefore “it prints garbage” is too weak a description.

Exercise 8.2

Consider int f(int *p){ return p[0] + p[1]; }. What assumptions are required for a call to f(p) to be valid?

p must point to an object (or appropriate contiguous sequence) for which reading two int elements is valid. The storage must have an appropriate lifetime and type/access semantics. If it points to a single int, the second read is invalid.

Exercise 8.3

Explain strict aliasing in practical terms. Why can it affect optimization?

The language places restrictions on which object types may legally be accessed through a pointer/reference of another type. These rules allow compilers to assume that certain differently typed accesses do not refer to the same object, enabling load/store reordering and register caching. Violating the rules can produce undefined behavior and surprising optimized results. Use appropriate techniques such as memcpy for representation copying or correct unions/character access according to the language rules and compiler environment.

Exercise 8.4

You see this code: float y = *(float*)&u;, where u is an unsigned integer. What concern should immediately come to mind?

Type-punning through an incompatible pointer can violate aliasing/object-model rules. The safe, portable approach in modern C++ is generally to use std::memcpy or an appropriate bit-cast facility when available. In C, memcpy is the common portable representation-copying technique.

Exercise 8.5

Why can restrict (C) help a DSP kernel? Give a concrete scenario.

If the programmer can guarantee that certain pointer-based accesses do not alias, restrict communicates that promise to the compiler. That can permit keeping values in registers, vectorizing, and reordering loads/stores more aggressively. It is only beneficial if the promise is true; violating the contract is dangerous.

void add(float * restrict y,
         const float * restrict a,
         const float * restrict b,
         int n) {
    for(int i=0;i<n;i++) y[i]=a[i]+b[i];
}

Exercise 8.6

What is the difference between shallow copy, deep copy, move construction, and copy elision in C++?

Shallow copy: copies representation/handles, potentially leaving two objects referring to the same resource. Deep copy: creates an independent resource. Move: transfers ownership/resources from a source object that can be left in a valid but unspecified state. Copy elision: the language/compiler can omit a copy/move in situations where a temporary result can be constructed directly in its destination. For performance code, understand ownership first; do not manually optimize away abstractions without measuring.

Exercise 8.7

Write an in-place stable partition of an array into negative and non-negative values using O(1) extra memory. Then discuss complexity.

A simple rotation-based stable algorithm can be written with O(n²) worst-case time and O(1) extra space. The important interview point is recognizing the trade-off: strict stability + constant auxiliary memory can make the straightforward algorithm quadratic. If O(n) is required, additional memory or a more sophisticated algorithm is needed. Do not claim O(n) without explaining the mechanism.

Exercise 8.8

A C++ function takes std::vector<float> by value in a hot path. Give three questions before changing it to a reference.
  1. Is a copy actually occurring on the hot path?
  2. Does the function need ownership/mutation semantics?
  3. What does profiling show about copy cost versus the rest of the workload?

Then choose const std::vector<float>&, std::span<const float>, pointer+length, or another interface based on API needs. A span-like view is often more general when ownership is not required.

Exercise 8.9

Implement a safe saturating addition for signed 32-bit integers without invoking signed-overflow UB.

One robust approach is to perform the addition in a wider type if the implementation guarantees that wider type can represent all possible sums, then clamp to INT32_MIN/MAX. Alternatively, check operands before adding. The key is: do not compute a signed overflowing expression and only then try to detect it.

int32_t sat_add(int32_t a, int32_t b) {
    int64_t s = (int64_t)a + (int64_t)b;
    if (s > INT32_MAX) return INT32_MAX;
    if (s < INT32_MIN) return INT32_MIN;
    return (int32_t)s;
}
