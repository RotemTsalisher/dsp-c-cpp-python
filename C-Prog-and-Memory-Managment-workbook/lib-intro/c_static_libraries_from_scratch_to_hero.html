Static Libraries in C

A practical course that takes you from “what is a library?” to building, packaging, linking, debugging and maintaining a reusable C static library in a completely separate project.

Assumption: you already write C comfortably, but have no library/build-system experience. Examples use GCC or Clang and work conceptually on Linux, macOS and Windows with MinGW. Windows/MSVC notes are included where useful.

Prerequisites and tools

  • A C compiler: GCC or Clang. Check with gcc --version or clang --version.
  • An archiver: usually ar, shipped with GNU binutils.
  • A terminal. On Windows, use MSYS2/MinGW-w64 or an equivalent GCC toolchain.
Important distinction: a static library is not a magical executable and does not run by itself. It is an archive of object files. The linker copies the needed machine-code sections from that archive into the final executable (or another library).
Module 01 • Concepts

What exactly is a static library?

A C program usually moves through these stages:

source code (.c)
     │  compiler: preprocess + compile
     ▼
object file (.o / .obj)
     │  linker + other objects/libraries
     ▼
executable (program)

A static library groups one or more object files into an archive, commonly named libNAME.a on Unix-like systems. It lets another project reuse compiled code without recompiling the library's source files every time.

FileWhat it contains / does
math.cFunction implementations.
math.hPublic declarations clients compile against.
math.oCompiled machine code plus symbol/relocation information.
libmathkit.aArchive containing object files.
main / app.exeFinal linked executable.

Static vs shared library

  • Static: selected object code is incorporated into the executable at link time. The resulting executable generally does not need the library file at runtime.
  • Shared/dynamic: code remains in a separate shared object/DLL and is loaded at runtime. This course focuses on static libraries.
Do not confuse static linking with “all code is always copied”. Traditional archive linking normally extracts archive members to satisfy unresolved symbols. Linker options, whole-archive behavior, LTO and section garbage collection can change details.
Exercise 1 — Explain it in your own words

What is the difference between a .c, .o, .a and executable? Why does a consumer still need the header?

A .c is source code; a .o is compiled object code; a .a is an archive of object files; an executable is the final linked program. The header gives the compiler declarations and types while compiling the consumer. The archive supplies the compiled definitions later, during linking.
Module 02 • First compilation

Compile C into object files

Before creating a library, compile a tiny function into an object file. Create this folder:

static-lib-course/
├── calc.c
└── calc.h

calc.h:

#ifndef CALC_H
#define CALC_H

int add(int a, int b);

#endif

calc.c:

#include "calc.h"

int add(int a, int b)
{
    return a + b;
}

Compile only; do not link an executable yet:

gcc -Wall -Wextra -Wpedantic -std=c11 -c calc.c -o calc.o

Read the command: -c means “compile/assemble, but do not link”. -o calc.o chooses the output filename. Warnings help catch mistakes early.

Inspect the object

file calc.o
nm calc.o

nm lists symbols. You should see add as a defined text symbol (often marked T). Exact output varies by platform.

Exercise 2 — Make an object file

Create calc.c and calc.h, compile with the command above, and confirm calc.o exists. Then deliberately misspell the function name in the declaration and observe what does (and does not) happen during compilation.

The compile command creates calc.o. A declaration spelling mismatch may not stop compilation of calc.c if that file does not use the declaration in a conflicting way. The mismatch usually becomes a linker error when a consumer calls the declared name but the object defines a different name. This illustrates why headers and definitions must agree.
Module 03 • Build the archive

Create your first static library

Now package the object file using ar (the archiver):

ar rcs libcalc.a calc.o
  • r: insert/replace members in the archive.
  • c: create the archive if it does not exist.
  • s: write/update the symbol index (often called the archive index).

Inspect it:

ar t libcalc.a
nm -s libcalc.a

ar t lists archive members; it should list calc.o. nm can show symbols in the archive.

The library is now built. It is named libcalc.a because many Unix-like linkers search for a library named calc when passed -lcalc.
Exercise 3 — Add a second source file

Create subtract.c and subtract.h (or put both declarations in calc.h). Compile it to subtract.o and rebuild the archive so it contains both object files.

/* subtract.c */
int subtract(int a, int b)
{
    return a - b;
}

/* commands */
gcc -Wall -Wextra -Wpedantic -std=c11 -c subtract.c -o subtract.o
ar rcs libcalc.a calc.o subtract.o
ar t libcalc.a
Run ar t and verify both members are listed. Re-running ar rcs updates/replaces members with matching names; it does not automatically remove old members whose names are no longer supplied.
Module 04 • Linking

Use the library in an executable

Create main.c:

#include 
#include "calc.h"

int add(int a, int b); /* remove this if calc.h already declares it */

int main(void)
{
    printf("2 + 3 = %d\\n", add(2, 3));
    return 0;
}

Link the object and archive directly:

gcc -Wall -Wextra -Wpedantic -std=c11 main.c ./libcalc.a -o demo

Or use the conventional library search syntax:

gcc -Wall -Wextra -Wpedantic -std=c11 -I. -L. main.c -lcalc -o demo
  • -I. adds the current directory to the header search path.
  • -L. adds the current directory to the library search path.
  • -lcalc asks the linker to find libcalc.a (or a shared-library alternative, depending on platform and linker settings).

Run it: ./demo on Linux/macOS, or .\demo.exe in PowerShell if built as demo.exe.

Link order matters with many Unix linkers. Put objects that reference symbols before the libraries that provide them: main.o -lcalc, not usually -lcalc main.o. Static archives are searched to resolve symbols encountered so far.
Exercise 4 — Break the link on purpose

Try compiling main.c without libcalc.a. Then try with the wrong library name (-lcal). Read the errors and explain which stage failed.

Without the archive, compilation of main.c can succeed because the header declares add, but linking fails with an “undefined reference” / unresolved external symbol. With -lcal, the linker cannot find a matching library. Header inclusion is a compile-time operation; finding function implementations is a link-time operation.
Module 05 • Public API design

Design a library like a professional

A good library separates its public interface from private implementation details.

calc-library/
├── include/
│   └── calc/
│       └── calc.h       # public header
├── src/
│   ├── calc.c           # implementation
│   └── internal.h       # private header, if needed
└── build/               # generated files

Public header example:

#ifndef CALC_CALC_H
#define CALC_CALC_H

#ifdef __cplusplus
extern "C" {
#endif

typedef struct {
    int value;
} CalcResult;

/* Returns 0 on success; writes the result to out_result. */
int calc_add(int a, int b, CalcResult *out_result);

#ifdef __cplusplus
}
#endif

#endif

Implementation:

#include "calc/calc.h"

int calc_add(int a, int b, CalcResult *out_result)
{
    if (out_result == 0) {
        return -1;
    }

    out_result->value = a + b;
    return 0;
}

API rules worth adopting

  • Use include guards in every public header.
  • Document ownership, valid inputs, return values and error behavior.
  • Do not expose private structs or implementation-only declarations unless needed.
  • Prefix public symbols (e.g. calc_) to reduce name collisions.
  • Avoid defining non-static functions or global variables in headers.
  • Use static for file-private helper functions.
  • Be cautious changing public struct layouts or function signatures: consumers must be rebuilt and the API may break.
Exercise 5 — Make the API safer

Change calc_add so it returns an error if out_result is null. Add a test in the consumer project for the null case.

The implementation above already checks for a null pointer and returns -1. In the client: 
if (calc_add(2, 3, NULL) != -1) {
    puts("null-input test failed");
    return 1;
}
Include <stddef.h> if you want to use NULL portably.
Module 06 • Separate consumer project

Package the library and use it elsewhere

This is the central real-world skill: the application should not need the library's .c source files. It needs only the public headers and the compiled archive.

Library project

calc-library/
├── include/calc/calc.h
├── src/calc.c
└── build/libcalc.a

Build from the library root:

mkdir -p build
gcc -std=c11 -Wall -Wextra -Wpedantic -Iinclude -c src/calc.c -o build/calc.o
ar rcs build/libcalc.a build/calc.o

Consumer project — a separate directory

calculator-app/
├── src/main.c
└── (no calc.c here!)

Copy or install the public include directory and archive into a package location, for example:

third_party/calc/
├── include/calc/calc.h
└── lib/libcalc.a

Compile the app from its own directory:

gcc -std=c11 -Wall -Wextra -Wpedantic \\
    -Ithird_party/calc/include \\
    src/main.c \\
    -Lthird_party/calc/lib -lcalc \\
    -o calculator

On Windows PowerShell, put the command on one line or use PowerShell's backtick for line continuation. With MinGW, the archive is commonly still libcalc.a.

Proof of separation: temporarily rename or move calc-library/src/calc.c. The consumer should still build using the packaged header and archive. If it cannot, you are probably compiling library source as part of the app instead of consuming the library artifact.
Exercise 6 — The two-project test

Create the two directories exactly as shown. Build the archive in the library project, copy only the public header and .a into the consumer, then build the consumer. Do not add calc.c to the consumer's compile command.

The key is that the client command names only src/main.c, the include directory, and the library directory/name. Example: 
gcc -Ithird_party/calc/include src/main.c -Lthird_party/calc/lib -lcalc -o calculator
The compiler reads the copied header. The linker extracts the required object member from libcalc.a. The original source file is not required for this build.
Module 07 • Debugging

Understand linker errors and inspect symbols

SymptomLikely causeCheck
undefined referenceImplementation absent, wrong link order, wrong library, or symbol name mismatch.nm libcalc.a; inspect link command.
cannot find -lcalcLibrary path/name incorrect.Check -L, filename and architecture.
Header not foundInclude path incorrect or header not packaged.Check -I and folder layout.
Multiple definitionSame global symbol defined in multiple objects; often function bodies in headers.Use declarations in headers, definitions in one .c.
Incompatible architecture / formatLibrary built for another target, object format or ABI.Use matching compiler/toolchain/target.

Useful inspection commands

ar t libcalc.a          # archive members
nm libcalc.a            # symbols
nm -A libcalc.a         # symbols with archive member names
objdump -f calc.o       # object format / architecture (GNU)
objdump -t calc.o       # symbol table
size calc.o             # section sizes (if supported)

Symbol convention: uppercase T commonly means a global function in a code section; lowercase t commonly means a local function. U means an undefined symbol that this object expects another object/library to provide. Output differs across platforms.

Exercise 7 — Diagnose an undefined reference

Your header declares int calc_multiply(int, int);, but the archive contains only calc.o with calc_add. Your app calls calc_multiply. What will happen, and how do you verify it?

The compiler accepts the call because the declaration exists. The linker fails because no linked object defines calc_multiply. Run nm -A libcalc.a; you will not find a defined calc_multiply symbol. Implement it, compile the new object, and rebuild the archive.
Module 08 • Automation

Build reliably with Make

Typing commands manually is useful for learning, but repeatable builds should be automated. Create a Makefile in the library project:

CC      := gcc
AR      := ar
CFLAGS  := -std=c11 -Wall -Wextra -Wpedantic -O2
CPPFLAGS := -Iinclude

BUILD   := build
LIB     := $(BUILD)/libcalc.a
OBJ     := $(BUILD)/calc.o

.PHONY: all clean

all: $(LIB)

$(BUILD):
	mkdir -p $(BUILD)

$(BUILD)/calc.o: src/calc.c include/calc/calc.h | $(BUILD)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

$(LIB): $(OBJ)
	$(AR) rcs $@ $^

clean:
	rm -rf $(BUILD)

Run make to build and make clean to remove generated output. Make uses tabs (not spaces) at the start of recipe lines. The vertical bar introduces an order-only prerequisite: the build directory must exist, but its timestamp alone should not force recompilation.

For a multi-source library, define one object per source and make the archive depend on all objects. When headers change, list the relevant headers as prerequisites. Larger projects often generate header dependencies automatically using compiler flags such as -MMD -MP.
Exercise 8 — Add a source file to Make

Add src/calc_subtract.c. Update the Makefile so it compiles the new source and packages both objects into the archive. Verify that touching the source rebuilds the right object and archive.

Use: 
OBJ := $(BUILD)/calc.o $(BUILD)/calc_subtract.o

$(BUILD)/calc_subtract.o: src/calc_subtract.c include/calc/calc.h | $(BUILD)
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

$(LIB): $(OBJ)
	$(AR) rcs $@ $^
Ensure the recipe lines begin with literal tab characters. Add the public header dependency if the source includes it.
Module 09 • Modern build systems

Build and consume the library with CMake

CMake describes targets and their relationships, then generates build files for a chosen backend. It is not itself the compiler.

Library CMakeLists.txt

cmake_minimum_required(VERSION 3.16)
project(calc VERSION 1.0.0 LANGUAGES C)

add_library(calc STATIC
    src/calc.c
)

target_include_directories(calc
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>
)

target_compile_features(calc PUBLIC c_std_11)

Build:

cmake -S . -B build
cmake --build build

The PUBLIC include directory is propagated to targets that link against calc. This is a major advantage over manually repeating include and library paths.

Consumer project

cmake_minimum_required(VERSION 3.16)
project(calculator_app LANGUAGES C)

add_subdirectory(third_party/calc)

add_executable(calculator src/main.c)
target_link_libraries(calculator PRIVATE calc)

Here third_party/calc contains the library's CMake project. Build the consumer with cmake -S . -B build then cmake --build build.

For a truly prebuilt third-party archive, you can define an IMPORTED target and set its archive location and interface include directory. Do not use add_subdirectory if you intentionally want to consume only a prebuilt binary package.
Exercise 9 — Make a target-based consumer

Build the library with CMake, then make a separate app that links to it. Confirm you do not need to manually write -I and -L flags in the app target.

Use target_include_directories(calc PUBLIC ...) in the library and target_link_libraries(calculator PRIVATE calc) in the app. CMake propagates the public usage requirements from the library target to the consumer.
Module 10 • Platform and architecture

Portability, compiler flags and binary compatibility

A static library is not universally interchangeable. Its object files are built for a specific target and toolchain environment.

  • Architecture: x86-64 objects cannot normally be linked into an ARM executable, and vice versa.
  • ABI: calling convention, data layout, alignment and symbol naming must agree.
  • Compiler/runtime: mixing toolchains can cause incompatible object formats or runtime assumptions.
  • Debug/release: debug symbols and optimization levels can differ; keep build configurations intentional.
  • 32-bit vs 64-bit: pointer sizes and data models differ. Build the library for the same target as the app.

Common naming differences

EnvironmentTypical static archiveObject file
GCC / Linuxlibcalc.a.o
Clang / macOSlibcalc.a.o
MSVCcalc.lib.obj
MinGW GCCusually libcalc.a.o

For MSVC, the broad process is analogous: compile source to .obj using cl /c, create a .lib archive with lib, then link the client with the archive and include path. Do not assume a GCC-built .a can be linked by MSVC.

Reproducible builds

Record compiler version, target architecture, relevant flags, library version and dependencies. Avoid compiling a library with machine-specific flags such as -march=native if you intend to distribute it to unknown machines.

Exercise 10 — Think like a release engineer

You built libcalc.a on an x86-64 Linux machine. A colleague tries to link it into an ARM embedded target and gets a file-format/architecture error. Is this a missing-header problem? What should you do?

No. The archive contains object code for the wrong target. Rebuild the library with the embedded target's cross-compiler and matching flags/sysroot/ABI, then link that target-specific archive into the embedded application. The public API may be portable, but the compiled binary is target-specific.
Module 11 • Advanced engineering

Dependencies, symbol visibility and release quality

Static library dependencies

Suppose libsignal.a calls functions from libmathkit.a. The final application must link both libraries, generally in dependency order:

gcc main.o -lsignal -lmathkit -o app

If archives depend on each other cyclically, linkers may need a group/repeated libraries, or the dependency structure should be redesigned. Prefer an acyclic dependency graph.

Do not put implementation bodies in public headers casually

A normal external function defined in a header included by several translation units can cause multiple-definition errors. For small header-only utilities, use static inline deliberately. For a traditional static library, put implementation in .c files.

Versioning and compatibility

  • Use semantic versioning as a communication convention: major for incompatible API changes, minor for backward-compatible features, patch for fixes.
  • Keep a changelog and document supported compiler/target combinations.
  • Ship headers, archive(s), license, README, build instructions and preferably tests.
  • Build and test the library independently, then test it from a clean consumer project.

Testing the library

Test public behavior through the public header, not by reaching into private implementation details. Run tests with warnings enabled and, where available, AddressSanitizer/UndefinedBehaviorSanitizer:

gcc -std=c11 -Wall -Wextra -Wpedantic -g \\
    -fsanitize=address,undefined \\
    test_calc.c src/calc.c -o test_calc

For a test of the compiled archive itself, link test_calc.c against libcalc.a rather than compiling the library source into the test executable.

Exercise 11 — Design a release package

List the files you would give another team so they can use version 1.0 of your library without your source tree. Include the information needed to avoid wrong-architecture and wrong-compiler problems.

A reasonable package contains include/ public headers, lib/ target-specific archive(s), README with exact compile/link or CMake usage, version and changelog, license, supported OS/architecture/compiler/ABI details, required dependent libraries and flags, and optionally tests/examples plus debug symbols. Separate builds by target/configuration, e.g. lib/linux-x86_64/ and lib/arm-none-eabi/.
Module 12 • Mastery checkpoint

Rapid-fire knowledge check

Q1. Does ar rcs libx.a x.o link an executable?
No. It creates/updates an archive. The final executable is produced by the linker in a separate command.
Q2. Does the consumer need the library's .c source at build time?
No, not when consuming the prebuilt archive. It needs public headers for compilation and the archive for linking.
Q3. What does -Lvendor/lib do? What does -Ivendor/include do?
-L adds a linker library search directory. -I adds a compiler header search directory.
Q4. Why might -lcalc fail even though libcalc.a exists?
The directory may not be in the linker's search path, the filename may not match platform conventions, the archive may be for the wrong target, or the command may use the wrong toolchain.
Q5. Why should a public header contain declarations rather than ordinary non-static function definitions?
Because many source files may include it. Repeating external function definitions across translation units can create duplicate symbols. Put ordinary definitions in one implementation file.
Final project • Hero challenge

Build a reusable DSP utility library

Build a small library that could realistically be reused in a C audio/DSP project. It should be compiled independently and consumed from a fresh application directory.

Requirements

  1. Create a library called libdsp_utils.a.
  2. Public headers under include/dsp/; implementation under src/.
  3. Implement at least: saturating conversion from int32_t to int16_t, RMS calculation for a float buffer, and a helper that applies gain to a float buffer.
  4. Define behavior for null pointers, zero-length buffers and invalid arguments.
  5. Build with -std=c11 -Wall -Wextra -Wpedantic.
  6. Provide a Makefile or CMake project.
  7. Package only headers + archive + README into a separate consumer project.
  8. Write consumer tests that link against the archive, not the library source.
  9. Inspect the archive with ar t and nm.
  10. Demonstrate that the consumer builds after the original source folder is unavailable.

Suggested API (you implement it)

/* include/dsp/dsp_utils.h */
#ifndef DSP_UTILS_H
#define DSP_UTILS_H

#include <stddef.h>
#include <stdint.h>

int16_t dsp_saturate_i32_to_i16(int32_t input);
int dsp_rms_f32(const float *samples, size_t count, float *out_rms);
int dsp_apply_gain_f32(float *samples, size_t count, float gain);

#endif
Design decision: document whether zero samples is an error or produces RMS = 0. Either can be defensible; consistency and clear documentation matter. Avoid silently accepting invalid pointers.
Capstone review checklist
  • Can a clean client include <dsp/dsp_utils.h>?
  • Does the client link without any library .c files?
  • Are all required symbols present in libdsp_utils.a?
  • Do errors explain missing headers vs missing symbols vs wrong architecture?
  • Can another developer reproduce the build from the README?
  • Have you tested edge cases and documented API behavior?

This is one valid implementation. It rejects null pointers when a non-zero count requires data, and treats zero-length RMS as an error.

/* src/dsp_utils.c */
#include "dsp/dsp_utils.h"
#include <math.h>

int16_t dsp_saturate_i32_to_i16(int32_t x)
{
    if (x > INT16_MAX) return INT16_MAX;
    if (x < INT16_MIN) return INT16_MIN;
    return (int16_t)x;
}

int dsp_rms_f32(const float *samples, size_t count, float *out_rms)
{
    if (samples == NULL || out_rms == NULL || count == 0) return -1;

    double sum = 0.0;
    for (size_t i = 0; i < count; ++i) {
        double x = samples[i];
        sum += x * x;
    }
    *out_rms = (float)sqrt(sum / (double)count);
    return 0;
}

int dsp_apply_gain_f32(float *samples, size_t count, float gain)
{
    if (samples == NULL && count != 0) return -1;
    for (size_t i = 0; i < count; ++i) samples[i] *= gain;
    return 0;
}

Build command (add -lm when linking on platforms where sqrt is in libm):

gcc -std=c11 -Wall -Wextra -Wpedantic -Iinclude -c src/dsp_utils.c -o dsp_utils.o
ar rcs libdsp_utils.a dsp_utils.o

Consumer link example:

gcc -std=c11 -Wall -Wextra -Wpedantic \\
    -Ithird_party/dsp_utils/include app.c \\
    -Lthird_party/dsp_utils/lib -ldsp_utils -lm -o app

For a production implementation, consider finite-value policy, overflow/precision behavior, alignment/vectorization expectations and whether the API should return a richer error enum.

Cheat sheet

The essential command sequence

# 1. Compile source into object code
gcc -std=c11 -Wall -Wextra -Wpedantic -Iinclude -c src/calc.c -o build/calc.o

# 2. Package object(s) into a static archive

# 3. Inspect the archive

# 5. Run
./app
