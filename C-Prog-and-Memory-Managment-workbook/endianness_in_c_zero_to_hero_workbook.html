Lesson 1 · Foundations

What exactly is stored in memory?

A computer's memory is a sequence of addressable locations. In C, a byte is the size of one addressable C memory unit (sizeof(char) is always 1). On virtually all modern systems, a byte contains 8 bits; the C standard does not require that, so technically a byte is CHAR_BIT bits.

A bit is either 0 or 1. A byte made of 8 bits can represent 256 different patterns: 00000000 through 11111111, or 0 through 255 when interpreted as an unsigned value.

One byte

000000000
000000011
11111111255

A value that needs more than one byte (for example, a 32-bit integer) occupies multiple consecutive memory bytes. The question endianness answers is: which byte goes at the lowest memory address?

Keep these ideas separate: a number's mathematical value, its bit representation, and the order in which its bytes are placed in memory are three different things.

Lesson 2 · The core concept

Little-endian vs. big-endian

Consider the 32-bit hexadecimal value 0x12345678. It consists of four bytes:

12most significant
34
56
78least significant

Big-endian: the most significant byte is stored at the lowest address.

Address+0+1+2+3
Big-endian12345678

Little-endian: the least significant byte is stored at the lowest address.

Address+0+1+2+3
Little-endian78563412
Memory aid: “little” means the little-end (least significant byte) comes first in memory. “Big” means the big-end (most significant byte) comes first.

Important: endianness does not reverse bits

In the byte 0x12, the bits are still 00010010. Endianness changes the order of whole bytes in a multi-byte value, not the bit order inside each byte.

Lesson 4 · C lab

Detect the machine's byte order

In C, an object's bytes can be inspected through a character pointer. The C standard permits inspecting an object's representation through a pointer to a character type.

#include <stdio.h>
#include <stdint.h>

int main(void)
{
    uint32_t value = UINT32_C(0x12345678);
    const unsigned char *bytes = (const unsigned char *)&value;

    for (size_t i = 0; i < sizeof value; ++i) {
        printf("byte %zu = 0x%02X\n", i, bytes[i]);
    }

    return 0;
}

Compile and run:

gcc -std=c11 -Wall -Wextra -Wpedantic endian.c -o endian
./endian

If the output begins 78 56 34 12, the machine stores this integer little-endian. If it begins 12 34 56 78, it stores it big-endian.

Do not assume the result in advance. Your program reports the byte order used for that object on the machine where it runs. Some architectures and data formats can have more complicated or context-dependent rules, so avoid assuming every platform is one of only two possibilities.

Lesson 5 · Common traps

Pointer casts, unions, and portability

1. A pointer cast does not convert the number

uint32_t x = 0x12345678;
unsigned char *p = (unsigned char *)&x;

This does not change x. It gives you a way to look at the bytes that make up its in-memory representation. The order you observe depends on the platform's representation.

2. A union is not a portable file-format solution

union Example {
    uint32_t value;
    unsigned char bytes[4];
};

On common compilers, writing value and reading bytes is a familiar way to inspect representation, but it is not a portable way to define a network or file format. It also assumes the integer is exactly four bytes. Prefer the character-pointer inspection shown in Lesson 4 for this learning exercise, and explicit shifts/masks for portable encoding.

3. Integer width matters

Use exact-width types such as uint32_t when you specifically need 32 bits. These typedefs are provided when the implementation has a type with exactly that width. Plain int is not guaranteed to be 32 bits.

4. Endianness is not the same as signedness

Signed vs. unsigned determines how a bit pattern is interpreted as a numeric value. Endianness determines the order of bytes in memory. They answer different questions.

Lesson 6 · Real-world engineering

Portable encoding and decoding

When writing a file, packet, or hardware protocol, define the byte order yourself. Do not rely on the host CPU's native byte order.

Encode a 32-bit value as big-endian bytes

#include <stdint.h>

void encode_u32_be(uint32_t value, uint8_t out[4])
{
    out[0] = (uint8_t)(value >> 24);
    out[1] = (uint8_t)(value >> 16);
    out[2] = (uint8_t)(value >> 8);
    out[3] = (uint8_t)value;
}

Shifting moves the desired byte into the lowest 8 bits; conversion to uint8_t keeps that byte. This produces the same byte sequence on little-endian and big-endian CPUs.

Decode four big-endian bytes

uint32_t decode_u32_be(const uint8_t in[4])
{
    return ((uint32_t)in[0] << 24) |
           ((uint32_t)in[1] << 16) |
           ((uint32_t)in[2] <<  8) |
           ((uint32_t)in[3]);
}

The casts before shifting are important: they ensure the operation is performed using an unsigned 32-bit type rather than relying on signed integer behavior.

Engineering rule: native memory representation is for working with local objects. A defined byte sequence is for communicating with files, networks, devices, and other machines.

Reference sheet

What you should remember

  • Endianness describes the order of bytes in a multi-byte object in memory.
  • Little-endian: least significant byte at the lowest address.
  • Big-endian: most significant byte at the lowest address.
  • It does not reverse the bits inside a byte.
  • Inspect native representation through an unsigned char pointer.
  • Use explicit shifts and masks to define portable file/protocol formats.
  • Use fixed-width integer types when the format requires a specific width.
  • Follow the hardware or protocol documentation; do not assume its byte order.

Part 2 · Memory layout and pointers

Investigate memory in C: addresses, alignment, and padding

This part follows the same lab method throughout: predict first → compile and run → compare → explain. The exact addresses will change between runs and machines. Your job is to understand the relationships and rules, not to guess a particular address.

Important reality check: C does not promise that local variables are placed on the stack in declaration order, or even that every local variable has a memory address during optimized execution. Address-taking, compiler, optimization level, ABI, debugger, and runtime environment all matter.

Set up your lab

Save each exercise as a separate .c file. With GCC or Clang, start with a learning-friendly build:

gcc -std=c11 -Wall -Wextra -Wpedantic -O0 -g lab.c -o lab
./lab

Then compare with optimization enabled:

gcc -std=c11 -Wall -Wextra -Wpedantic -O2 lab.c -o lab_opt
./lab_opt

On Windows, run lab.exe / lab_opt.exe. For consistent experiments, use the same compiler and machine when comparing these two builds.

Part 2 · Exercise 1 · Beginner

What is an address? What does %p print?

In C, &variable means “the address of this variable”. The %p format specifier prints a pointer value. Pass a void * argument to %p, so cast object pointers as (void *)&variable.

Predict before running

Without running the code, answer these:

  1. Will &a and &b be equal?
  2. Will &a be numerically smaller than &b?
  3. Can you know the exact addresses before running the program?

Run this code

#include <stdio.h>

int main(void)
{
    int a = 10;
    int b = 20;

    printf("a: value=%d, address=%p\n", a, (void *)&a);
    printf("b: value=%d, address=%p\n", b, (void *)&b);

    return 0;
}

Record what happened

Paste your output or write down the two addresses. Then calculate whether the address of a is above or below the address of b.

Detailed explanation

The two variables are distinct objects, so their storage does not overlap while both are alive. But C does not guarantee which one has the lower address. Compilers and ABIs choose a layout that suits their implementation. You should expect different addresses across runs, builds, machines, and debugging configurations.

Also, do not assume the addresses are adjacent. The compiler may leave gaps, use different stack slots, or keep values in registers when their addresses are not needed.

Part 2 · Exercise 2 · Beginner

sizeof(int) vs sizeof(pointer)

sizeof(int) is the size of an int object. sizeof(int *) is the size of an object whose type is “pointer to int”. They are different types and can have different sizes.

#include <stdio.h>

int main(void)
{
    int value = 123;
    int *ptr = &value;

    printf("sizeof(char)   = %zu\n", sizeof(char));
    printf("sizeof(int)    = %zu\n", sizeof(int));
    printf("sizeof(int *)  = %zu\n", sizeof(int *));
    printf("sizeof(ptr)    = %zu\n", sizeof ptr);
    printf("sizeof(*ptr)   = %zu\n", sizeof *ptr);

    return 0;
}

Predict first

  1. What do you expect sizeof(int) to print?
  2. What do you expect sizeof(int *) to print on a typical 32-bit system?
  3. What do you expect it to print on a typical 64-bit system?
  4. What is the difference between sizeof ptr and sizeof *ptr?
Detailed explanation

On many common systems, sizeof(int) is 4 bytes. On a typical ILP32 32-bit data model, pointers are 4 bytes. On a typical LP64 64-bit data model, pointers are 8 bytes while int remains 4 bytes.

That is a common platform convention, not a universal C rule. C does not require int to be 4 bytes, nor does “64-bit CPU” alone fully specify every C type size. Use sizeof on the target you compile for.

sizeof ptr measures the pointer object. sizeof *ptr measures the pointed-to int. The expression inside sizeof is not evaluated here, so this particular use does not dereference the pointer at runtime.

Part 2 · Exercise 3 · Beginner → Intermediate

Calculate byte distances correctly

Addresses are often displayed in hexadecimal. Hexadecimal is base 16: each digit represents 0–15. For example, 0x20 - 0x04 = 0x1C, and 0x1C is 28 in decimal.

Do not subtract pointer values as integers in portable C. Pointer subtraction with ptr1 - ptr2 is defined when both point into the same array object (or one past it), and the result is measured in elements, not bytes. For byte offsets inside an object's representation, use an unsigned char * pointer.

Prediction drill

Calculate each distance before checking:

  1. 0x08 - 0x04
  2. 0x20 - 0x08
  3. 0x100 - 0xF8
  4. 0x2C - 0x10

Run this byte-distance experiment

#include <stdio.h>
#include <stddef.h>

int main(void)
{
    int values[4] = { 10, 20, 30, 40 };
    int *first = &values[0];
    int *third = &values[2];

    ptrdiff_t element_distance = third - first;
    const unsigned char *first_byte = (const unsigned char *)first;
    const unsigned char *third_byte = (const unsigned char *)third;
    ptrdiff_t byte_distance = third_byte - first_byte;

    printf("sizeof(int)       = %zu\n", sizeof(int));
    printf("element distance  = %td\n", element_distance);
    printf("byte distance     = %td\n", byte_distance);

    return 0;
}

Predict first

How many elements apart are values[0] and values[2]? How many bytes apart do you expect them to be if sizeof(int) is 4?

Detailed explanation

Both pointers point into the same array, so subtracting them is valid and gives 2 elements. The byte pointers also point into the same array object's byte representation, so their difference is the byte distance: 2 * sizeof(int). If sizeof(int) is 4, that is 8 bytes.

For unrelated local variables, do not use pointer subtraction to calculate their distance. C does not define subtraction for pointers to unrelated objects. You may inspect and print addresses for an experiment, but portable C does not provide a general-purpose “distance between arbitrary objects” operation.

Part 2 · Exercise 4 · Intermediate

Pointer alignment: why addresses have boundaries

Some types have alignment requirements. An object of a type must be placed at an address suitable for that type. Query the requirement with _Alignof(type) in C11.

#include <stdio.h>
#include <stdalign.h>
#include <stdint.h>

int main(void)
{
    char c = 'X';
    int i = 42;
    double d = 3.14;
    int *p = &i;

    printf("&c = %p, _Alignof(char)   = %zu\n", (void *)&c, _Alignof(char));
    printf("&i = %p, _Alignof(int)    = %zu\n", (void *)&i, _Alignof(int));
    printf("&d = %p, _Alignof(double) = %zu\n", (void *)&d, _Alignof(double));
    printf("&p = %p, _Alignof(int *)  = %zu\n", (void *)&p, _Alignof(int *));

    return 0;
}

Predict first

  1. Do you expect the address of p (the pointer variable itself) to be aligned for int *?
  2. Does an 8-byte pointer necessarily have 8-byte alignment?
  3. Does alignment mean every object of that type is exactly that many bytes long?
Detailed explanation

Object addresses satisfy the alignment requirement of their type. On many common 64-bit systems, pointer objects are 8 bytes in size and have 8-byte alignment, so their addresses are multiples of 8. But size and alignment are separate properties: an 8-byte object is not guaranteed by C to require 8-byte alignment.

Alignment is about which addresses are valid or efficient for an object type. It is not a promise about the object's size. Use sizeof and _Alignof to measure both on your target.

Part 2 · Exercise 5 · Intermediate

Padding inside structs

The compiler may insert unused bytes between structure members, or after the final member, so each member is correctly aligned and arrays of the structure keep each element aligned.

#include <stdio.h>
#include <stddef.h>

struct Example {
    char c;
    int i;
    char d;
};

int main(void)
{
    printf("sizeof(struct Example) = %zu\n", sizeof(struct Example));
    printf("_Alignof(struct Example) = %zu\n", _Alignof(struct Example));
    printf("offset c = %zu\n", offsetof(struct Example, c));
    printf("offset i = %zu\n", offsetof(struct Example, i));
    printf("offset d = %zu\n", offsetof(struct Example, d));
    return 0;
}

Predict first — assume common alignment

Assume sizeof(char)=1, sizeof(int)=4, and _Alignof(int)=4. Predict the offsets of c, i, and d, plus the total struct size.

Detailed explanation for the common layout

A typical layout is:

Byte offsetContents
0c
1–3Padding before i
4–7i
8d
9–11Tail padding

That gives offsets 0, 4, and 8, and a total size of 12 bytes on this common ABI. The C standard permits implementation-defined padding; confirm using offsetof and sizeof on your compiler.

Part 2 · Exercise 6 · Intermediate

Local variables, stack layout, and declaration order

The supplied diagram shows local variables and pointer relationships as a conceptual memory map. It is useful for learning, but treat the exact addresses and order as one possible illustrative layout—not a rule of C.

Key distinction: “local variable” describes scope and lifetime, not a guaranteed physical location. Many implementations place locals in a stack frame, but optimized code may keep values in registers, reuse stack slots, or remove objects whose addresses are never needed.
#include <stdio.h>

int main(void)
{
    int v1 = 1;
    int v2 = 2;
    int checkpoint = 0;

    printf("&v1         = %p\n", (void *)&v1);
    printf("&v2         = %p\n", (void *)&v2);
    printf("&checkpoint= %p\n", (void *)&checkpoint);

    printf("distance v1-v2 is NOT portably computed by pointer subtraction\n");
    return 0;
}

Predict first

  1. Will v1 necessarily have a lower address than v2 because it was declared first?
  2. Will checkpoint necessarily follow v2 in memory?
  3. Would you expect the output to be identical under -O0 and -O2?
Detailed explanation

No declaration-order guarantee exists for local variable addresses. The compiler and ABI decide the stack-frame layout. On some systems the stack grows toward lower addresses, but that does not mean local declarations map directly in reverse order. Padding, saved registers, spills, stack alignment, and optimization can all affect the frame.

Compare the same program built with -O0 and -O2. Taking each variable's address and printing it makes the addresses observable, so the compiler must provide addressable storage for those objects in this program. Even then, their relative ordering is not specified by C.

Part 2 · Exercise 7 · Intermediate

Pointer, pointer value, and pointed-to value

This is the most important mental model in the supplied example. There are three distinct things:

ExpressionMeaning
ptrThe value stored inside the pointer variable: an address
&ptrThe address where the pointer variable itself is stored
*ptrThe object/value at the address stored in ptr

Run the pointer-to-pointer example

#include <stdio.h>

int main(void)
{
    int v1 = 1;
    int v2 = 2;
    int checkpoint = 0;

    int *ptr = &v1;
    int **ptr_ptr = &ptr;

    checkpoint = **ptr_ptr;

    printf("v1 address       &v1       = %p\n", (void *)&v1);
    printf("ptr value        ptr       = %p\n", (void *)ptr);
    printf("ptr address      &ptr      = %p\n", (void *)&ptr);
    printf("ptr_ptr value    ptr_ptr   = %p\n", (void *)ptr_ptr);
    printf("ptr_ptr address  &ptr_ptr = %p\n", (void *)&ptr_ptr);
    printf("*ptr             = %d\n", *ptr);
    printf("**ptr_ptr        = %d\n", **ptr_ptr);
    printf("checkpoint       = %d\n", checkpoint);

    ptr = &v2;
    checkpoint = **ptr_ptr;

    printf("\nAfter ptr = &v2:\n");
    printf("ptr value        = %p\n", (void *)ptr);
    printf("*ptr             = %d\n", *ptr);
    printf("**ptr_ptr        = %d\n", **ptr_ptr);
    printf("checkpoint       = %d\n", checkpoint);

    return 0;
}

Predict the relationships before running

  1. Is ptr equal to &v1 initially?
  2. Is ptr_ptr equal to &ptr?
  3. What does **ptr_ptr evaluate to initially?
  4. After ptr = &v2, does ptr_ptr change?
  5. After that assignment, what does **ptr_ptr evaluate to?
Detailed explanation — follow the arrows

Initially, ptr stores the address of v1. The pointer variable ptr itself lives somewhere else, and &ptr is that location. ptr_ptr stores &ptr.

ptr_ptr  ──points to──>  ptr  ──points to──>  v1
  int **                 int *                 int

Therefore *ptr_ptr means “read the pointer value stored in ptr”, which is the address of v1. Then **ptr_ptr follows that address and reads the integer value 1.

When you execute ptr = &v2, you change the value stored in ptr. You do not change the address of the pointer variable itself, so ptr_ptr still points to ptr. Now **ptr_ptr reads 2.

Part 2 · Exercise 9 · Advanced

Alignment by experiment with _Alignas

C11 lets you request stricter alignment using _Alignas, subject to implementation support and the type's alignment constraints.

#include <stdio.h>
#include <stdalign.h>

int main(void)
{
    _Alignas(16) int special = 7;
    int ordinary = 8;

    printf("&special = %p\n", (void *)&special);
    printf("&ordinary= %p\n", (void *)&ordinary);
    printf("_Alignof(int) = %zu\n", _Alignof(int));
    return 0;
}

Predict first

Will the address of special be divisible by 16 when interpreted as an address? Will ordinary also be 16-byte aligned? Explain what you expect, then run it.

Detailed explanation

_Alignas(16) requests at least 16-byte alignment for special. It does not require the next local variable to have the same alignment. The compiler may happen to align more objects, but only the requested and type-required constraints are relevant. This example is useful for observing alignment, not for inferring stack direction or declaration order.

Part 2 · Exercise 10 · Advanced

Optimization: stack slot, register, or no object?

Compare these two functions. The first never exposes the address of its local variable. The second prints its address.

#include <stdio.h>

int compute_without_address(void)
{
    int local = 123;
    return local + 1;
}

int compute_with_address(void)
{
    int local = 123;
    printf("local address = %p\n", (void *)&local);
    return local + 1;
}

int main(void)
{
    printf("result 1 = %d\n", compute_without_address());
    printf("result 2 = %d\n", compute_with_address());
    return 0;
}

Predict first

  1. Does the first function need to put local in memory at all?
  2. Does the second function need an addressable object for local?
  3. Will the two functions necessarily have the same machine-code implementation under -O2?
Detailed explanation

The first function's result can be computed without creating a stack slot for local; the compiler may constant-fold the result. In the second function, the program prints the object's address, so an addressable object must exist for the duration of that use. The compiler can still optimize surrounding code.
