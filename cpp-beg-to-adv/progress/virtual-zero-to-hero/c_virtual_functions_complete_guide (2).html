C++ Virtual Functions — Complete Beginner to Advanced Guide

Step 1: The Core Problem — Static Binding

By default, C++ decides which function to call at compile time. This is called static binding.

The rule is simple but dangerous:

  • The function is chosen based on the type of the pointer/reference
  • NOT based on the actual object in memory
class Base {
public:
    void speak() { std::cout << "Base" << std::endl; }
};

class Derived : public Base {
public:
    void speak() { std::cout << "Derived" << std::endl; }
};

Base* obj = new Derived();
obj->speak(); // Base ❌
Mental Model:
The compiler sees: "obj is Base* → call Base::speak"
It completely ignores the fact that the real object is Derived.

This breaks one of the most important ideas in OOP:

  • "Treat derived objects as base objects"
  • But still get correct behavior

Step 2: virtual = Runtime Decision

The virtual keyword changes everything:

  • Function resolution is delayed to runtime
  • The program checks the actual object type
class Base {
public:
    virtual void speak() { std::cout << "Base" << std::endl; }
};

class Derived : public Base {
public:
    void speak() override { std::cout << "Derived" << std::endl; }
};

Base* obj = new Derived();
obj->speak(); // Derived ✅
Key Idea:
virtual enables runtime polymorphism → one interface, many behaviors.

Step 3: override — Your Safety Net

override ensures you're actually overriding something.

class Derived : public Base {
public:
    void speak(int x) override; // ❌ compiler error
};
Without override:
  • This would compile
  • But NOT override → creates a new function
  • Leads to silent bugs
Always use override. Treat it as mandatory.

Step 4: Virtual Destructors — Critical Rule

If a class has ANY virtual function → destructor should be virtual.

class Base {
public:
    virtual ~Base() {}
};
What happens without it?
  • delete base_ptr;
  • Only Base destructor runs
  • Derived part is NOT destroyed
  • → memory leaks / undefined behavior

Step 5: Pure Virtual Functions

A pure virtual function forces derived classes to implement behavior.

class Shape {
public:
    virtual void draw() = 0;
};
This creates an abstract class:
  • Cannot instantiate Shape
  • Used as an interface
  • Defines a contract

Step 6: Under the Hood — vtable Deep Dive

When a class has virtual functions, the compiler builds a vtable.

What is inside a vtable?
  • Function pointers
  • One entry per virtual function
Base vtable:
[ &Base::speak ]

Derived vtable:
[ &Derived::speak ]
What happens at runtime?
  1. Object contains hidden pointer (vptr)
  2. vptr → points to correct vtable
  3. Call goes through vtable
  4. Correct function is executed
Important: This mechanism is NOT in the C++ standard formally, but all major compilers use it.

Step 7: Memory Layout Explained

Derived object in memory:

[ vptr ] → Derived vtable
[ Base data ]
[ Derived data ]
Observations:
  • vptr is usually the first field
  • Added automatically
  • Invisible in your code

Step 8: Function Call Breakdown

Calling a virtual function roughly becomes:

obj->speak();

Internally behaves like:

obj->vptr[0](obj);
This is why:
  • Calls are slightly slower
  • But extremely flexible

Step 9: Multiple Inheritance Complexity

With multiple base classes:

  • Each base may introduce its own vptr
  • Object layout becomes more complex
This is one reason multiple inheritance is considered advanced.

Step 10: Performance Reality

  • vptr = +8 bytes (typically)
  • Indirect call = tiny overhead
  • Branch prediction usually makes it fast
In real systems:
  • Cost is negligible
  • Design clarity is more important

Step 11: Common Mistakes

  • Forgetting virtual destructor
  • Not using override
  • Calling virtual functions in constructors/destructors
Virtual calls inside constructors behave like NON-virtual calls.

Step 12: When NOT to Use virtual

  • Performance-critical inner loops
  • When behavior is known at compile time
  • Use templates instead (compile-time polymorphism)
