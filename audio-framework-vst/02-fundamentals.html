VST, AFW architecture & audio fundamentals

Concepts first — still no implementation. Everything below is mapped onto AudioFramework language (AudioModule, Calc, GenericProcessor.

Phase 1 — What is a VST?

1.1 Host · Plugin · DSP

DAW / Host VST Plugin DSP (your module) (Ableton, Reaper, (GenericProcessor (GainCalc / your Calc) Cubase, …) + JUCE VST3 wrapper) │ │ │ │ discovers & loads │ speaks VST3 API │ math on samples │ sends audio blocks → │ copies ↔ AudioModule → │ y = f(x, params) │ receives audio ←──── │ │ │ owns transport, │ owns UI / params │ owns algorithm state I/O, timeline
  • Host: discovers plugins, creates instances, calls prepare/process, manages buses and transport.
  • Plugin: implements the contract (in AFW: JUCE + GenericProcessor).
  • DSP: the actual signal algorithm (in AFW: C Core->Calc).

1.2 VST2 vs VST3 (what matters here)

  • This repo builds VST3 only (JucePlugin_Build_VST=0, JucePlugin_Build_VST3=1).
  • VST3 uses buses, a clearer parameter model, and a different binary packaging (.vst3 bundle/DLL on Windows).
  • You do not need VST2 history for AFW work — ignore VST2 except when debugging “why isn’t my host scanning VST2 folders?”

1.3 Lifecycle when a DAW loads a plugin

DAW starts ↓ Plugin discovery / scanning (looks in VST3 folders) ↓ Plugin binary loaded (.vst3 DLL) ↓ Factory / entry point createPluginFilter() ↓ Plugin instance created new GenericProcessor(setup, ioConfig) ↓ Initialization constructor: alloc buffers, Core->Init ↓ Sample rate configured prepareToPlay(sr, blockSize) ↓ Block size configured (may re-Init if size/layout changes) ↓ Processing starts ↓ Audio blocks arrive processBlock(...) ↓ Plugin processes them Core->Calc ↓ Processing stops ↓ Plugin destroyed Core->Free, free buffers

Map each stage to AFW files as you re-read Framework/GenericProcessor.cpp.

Level 1 — What?
A table of function pointers naming the module and its lifecycle APIs.
Level 2 — How?
GenericProcessor never calls GainCalc by name; it calls m_Setup->Core->Calc(m_Setup).
Level 3 — Why?
Same JUCE binary glue works for 70+ modules. New DSP = new C core + tiny Plugin.h, not a new C++ processor class.

Parameters & GUI

  • Module fills ParamInfo (name, unit, type, min/max/default).
  • Types include PT_SLIDER_LIN, PT_COMBO_BOX, PT_BUTTON, PT_METER, file dialogs, …
  • GenericEditor builds controls from that metadata. Optional custom DisplayComponent if HAS_DISPLAY_COMPONENT.
  • Host parameter changes → SetValue; meters/UI reads → GetValue.

processBlock bridge (actual AFW path)

// Simplified from GenericProcessor::processBlock
for each input channel i:
  copy host buffer → m_Setup->Inputs[i][0..BlockLength)
m_Setup->Core->Calc(m_Setup);
for each output channel i:
  copy m_Setup->Outputs[i] → host buffer

There is no processBlock in C modules. Your job is XxxCalc(AudioModule* setup).

Phase 3 — Audio processing fundamentals

Samples

A sample is one floating-point amplitude at one time instant, typically in about [-1, 1] for float plugins. AFW uses float buffers.

Channels

Independent streams (Left, Right, …). AFW: setup->NumInputs / NumOutputs, and Inputs[ch][sample].

Buffers & blocks

Hosts process blocks (e.g. 64, 128, 256, 512 samples) for efficiency and predictability. Never assume a fixed block size forever — prepareToPlay can change it.

BlockLength = 128 sample index: 0 1 2 … 127 per channel buffer: float[128]

Sample rate

  • 44.1 kHz — CD heritage
  • 48 kHz — common in pro/video; AFW constructor default often 48000
  • 96 kHz — higher bandwidth / headroom for processing

Filters, delays in ms, ramps — anything time-based — must use setup->SampleRate.

Stereo layout in AFW

Non-interleaved (planar) — what AFW uses: Inputs[0] → L0 L1 L2 … Inputs[1] → R0 R1 R2 … Interleaved (common elsewhere): L0 R0 L1 R1 L2 R2 …

JUCE’s AudioBuffer is also planar per channel. The copy loops in processBlock match that.

Phase 4 — Real-time audio programming

The audio callback (processBlock → Calc) runs on a high-priority thread with a deadline. Missing the deadline = glitches / dropouts.

What is generally safe in Calc?

  • Arithmetic on existing buffers
  • Reading preallocated state in Specific
  • Bounded loops over BlockLength and channel count
  • Lock-free parameter reads of values already stored in module state

What is unsafe / problematic?

C/C++ concepts you just touched

  • Function pointers — how AudioModuleCore achieves polymorphism in C
  • Opaque state — void* Specific cast to your struct
  • Ownership — who allocates buffers (processor) vs algorithm state (Init)
  • ABI / dynamic library — the .vst3 exports symbols the host finds via JUCE client code
