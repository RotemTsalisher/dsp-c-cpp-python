Three VST projects, capstone & expert assessment

Same AFW integration pattern every time. Difficulty rises in DSP, state, and independence. Study existing modules (Clipper, Delay, Compressor, Biquad) as references — do not blindly copy.

Per-project workflow (always) A Requirements → B DSP → C Architecture → D Repo integration → E Baby-step impl → F Incremental build → G Test → H Debug → I Refactor / senior review
Support taper Project 1: detailed guidance, you write almost everything.
Project 2: architecture + strong guidance.
Project 3: requirements + architecture + hints.
Capstone: specification only — mentor reviews.

VST Project 1 — Beginner+ · Soft Saturation

Why this fits AFW: Still one Calc, few params, teaches waveshaping and parameter ranges without delay lines. Related in-repo: Clipper, SoftMute.

A — Requirements

  • Stereo (and mono) in/out via ioConfigs
  • Parameters: Drive (dB or linear), Mix (dry/wet 0–1), optional Output gain
  • Algorithm: soft saturate, e.g. y = tanh(drive * x), then wet/dry
  • No custom GUI; GenericEditor only
  • Real-time safe Calc

B — DSP teaching stack

Why: tame peaks / add harmonics without hard clip bricks What: compresses large |x|, leaves small |x| almost linear Math: y = tanh(g·x) (or soft-clip polynomial) Difference eq: memoryless → y[n] = f(x[n]) (no state) Coeffs: g from Drive param C++/C: per-sample in Calc RT: precompute g in SetValue; no alloc Edges: g=0 → silence-ish; huge g → approaches sign(x) Test: sine → look at waveform/spectrum; unity-ish at low drive

C — Architecture

typedef struct {
  float DriveLinear;
  float Mix;
  float OutGain;
} SaturatorSetup;
/* AudioModuleCore Saturator = { ... }; */

D — Integration

Same as Part 1: Modules/Saturator/ from Template, Plugin.h, vcxproj, unique PluginCode.

E — Baby steps (mentor enforces STOP between)

  1. Folder + core declaration
  2. Init/Free state
  3. Passthrough Calc (prove wiring)
  4. Build + load
  5. Add tanh drive
  6. Add mix
  7. ParamInfo + Set/Get
  8. Full test list from Phase 10

I — Refactor prompts

Could you share drive across channels? Should mix be equal-power? Is tanhf cost OK at 8 channels?

VST Project 2 — Intermediate · Tempo-independent Delay

Why: Introduces DSP state, circular buffers, sample-rate-dependent length, parameter smoothing. Related in-repo: Modules/Delay — read after you design your own first pass.

A — Requirements

  • Delay time 1–1000 ms
  • Feedback 0–0.95 (clamp for stability)
  • Mix dry/wet
  • Max delay buffer allocated in Init from SampleRate × maxMs
  • Clear buffer on reset/Init
  • Document latency if you report any to the host (optional advanced)

B — DSP

Intuition: echo = play past input later Math: y[n] = mix·x[n-D] + (1-mix)·x[n] with feedback: buffer[w] = x[n] + fb·buffer[w-D] D = delayMs * SampleRate / 1000 State: circular buffer + write index RT: fixed max buffer; changing delay may interpolate (start with integer samples) Edges: fb≥1 unstable; D≥max wrap bugs; SR change → re-Init

C — Architecture sketch (you design details)

typedef struct {
  float* Buffer;   /* or per-channel */
  int Capacity;
  int WritePos;
  int DelaySamples;
  float Feedback;
  float Mix;
} DelaySetup;

Support level

Mentor helps architecture and review; you write most of Calc and index math. Progressive hints only when stuck.

Tests unique to delay

  • Impulse in → impulse out after ~D samples
  • Feedback decays
  • Change SR mid-session (re-prepare)
  • Zero delay ≈ dry (or 1-sample — document behavior)

VST Project 3 — Advanced · One-band dynamics (soft-knee compressor)

Why: Combines envelope follower, attack/release (SR-dependent coeffs), nonlinear gain computer, stereo linking. Related: Modules/Compressor, Limiter, NoiseGate — compare after your design review.

A — Requirements

  • Params: Threshold (dB), Ratio, Attack (ms), Release (ms), Makeup (dB), optional Knee
  • Stereo: shared gain from max(|L|,|R|) or mid detection (document choice)
  • Ballistics: different attack/release time constants
  • Meter param for gain reduction (PT_METER) if you want GenericEditor feedback
  • No allocations in Calc; coefficients updated on SetValue / SR change

B — DSP outline

Level detect → envelope (AT/RT) → gain computer (threshold/ratio/knee) → apply gain → makeup Coeffs: alpha = exp(-1/(timeSec*SR)) State: envelope, current gain RT: precompute alphas when params/SR change

Support level

Mentor gives requirements, architecture checklist, and hints. You design state layout, implement majority of code, own the test plan.

I — Senior refactor questions

  • Sidechain input? (out of scope unless you extend ioConfigs carefully)
  • Lookahead? (adds latency — host reporting)
  • Match AFW Compressor parameter UX for Tuning/XML later?

Final capstone — Independent design

No implementation provided Mentor acts only as senior reviewer. You design and implement.

Project: “AFW Channel Strip Lite”

Single VST module that chains internally (still one AudioModule Calc — not a multi-module afw graph unless you choose the advanced path).

Functional specification

  1. Input trim (dB)
  2. One biquad EQ band (peak or low shelf — pick one and document)
  3. Soft saturator (from Project 1 lessons)
  4. Output limiter / ceiling
  5. Bypass that truly skips processing (or use module Mode if integrating with framework modes)

Parameter specification

Define names, units, types, ranges, defaults in a table before coding. Include at least one combo box (e.g. EQ type) and one meter (output level or GR).

DSP requirements

  • SR-dependent EQ coefficients recomputed when freq/Q/gain/SR change
  • Filter state in Specific; clear on Init
  • Document processing order and why

Performance

  • Stable at 8 channels if ioConfigs allow it (or explicitly support only 2 and say so)
  • No heap in Calc; CPU budget: no obvious per-sample pow without need

Testing & acceptance

  • All Phase 10 tests plus EQ sweep sanity, limiter prevents |y|>ceiling
  • pluginval basic pass (or documented failures)
  • Written one-page design note: data flow diagram with real function names
  • Code review with mentor: ownership, RT safety, ParamInfo correctness

Expert readiness assessment

Use with a mentor. Mix oral + take-home.

Repository understanding

  • Draw Framework vs Modules vs VST3 folder responsibilities.
  • When must you touch AudioLibrary.c?

VST architecture & lifecycle

  • Walk createPluginFilter → prepareToPlay → processBlock → destructor.
  • What happens if NumInputs changes at runtime?

C / C++

  • Explain AudioModuleCore function pointers vs C++ virtual methods.
  • Who owns Inputs/Outputs vs Specific?

Audio / DSP / RT

  • Implement on paper: ms → samples; dB → linear.
  • Why feedback delay needs a clamp; what happens if you alloc the delay line in Calc?

Parameters & state

  • Given a ParamInfo array, sketch what GenericEditor will show.
  • Debug scenario: slider moves, audio unchanged — list hypotheses in order.

Build / debug / test

  • Linker error “unresolved Init” — causes?
  • Host shows old GUI — procedure?

Architecture problem

Product wants a new “NoiseReductionLite” module used in firmware graph and as VST. List exact repo touch points (from the official checklist) and what stays shared.

Implementation exercise

In 45–90 minutes: Template → module that does DC blocker (y[n] = x[n] − x[n−1] + R·y[n−1], pick R). Mentor reviews without giving code first.

Expert bar You can open AudioFramework and honestly say: “I know where the VST belongs, why, how the host talks to it, how audio flows, how to implement DSP, build, test, and debug it.”
