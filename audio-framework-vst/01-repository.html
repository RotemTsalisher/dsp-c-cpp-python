Repository reconnaissance

Before writing a single line of plugin code, build a mental map of this repository. Open your AudioFramework clone side-by-side with this page and verify each claim.

0.2 Build system

Not a top-level CMake module build. AFW modules use Visual Studio.

  • IDE / toolset: Visual Studio 2022, toolset v143, x64, Windows SDK 10
  • Languages: Module DSP in C; VST glue / JUCE in C++17
  • Plugin output: Dynamic library with extension .vst3
  • Master VST solution: Modules/VST3Plugins.sln
  • Per-plugin: Modules/<Name>/VST3/<Name>Plugin.sln
  • Desktop graph test: Builds/Win64/AudioFramework.sln
  • Embedded static lib: Builds/CSL_AFW/CSL_AFW.sln

How compilation works in this repo

Your Module.c + Framework C sources + GenericProcessor.cpp / GenericEditor.cpp + JUCE module .cpp files (listed in .vcxproj) │ ▼ MSVC compile (C / C++17) → .obj files │ ▼ Link as DynamicLibrary → Name.vst3 │ ▼ Post-build often copies to C:\Program Files\Common Files\VST3

Typical configs: Debug | x64 and Release | x64. Start with Debug while learning.

Command explanation example Opening Modules\Gain\VST3\GainPlugin.sln in Visual Studio and building GainPlugin | Release | x64 compiles that plugin only. Output lands under Modules\Gain\VST3\x64\Release\ (exact path may vary by project settings).

0.3 Find the audio pipeline

There are two related pipelines. Confusing them is a common beginner mistake.

A) Full framework graph (firmware / Win64 / Tuning backend)

afwCreate() ↓ afwAddModule() × N (from AudioLibrary registry) ↓ afwAddAudioLink() / afwLinkAll() ↓ afwInit() (wire I/O buffers) ↓ afwCalc() per block ↓ For each AudioModule: mode OFF/MUTE/BYPASS → special path else → am->Core->Calc(am) ↓ ParamLink propagation ↓ Framework Outputs

Key files: Framework/AudioFramework.c, Framework/AudioModule.h, Framework/AudioLibrary.c.

B) VST3 single-module path (what we use for plugins)

A VST3 does not run the full multi-module graph. It owns one AudioModule.

DAW / Host ↓ JUCE juce_audio_plugin_client_VST3 ↓ createPluginFilter() [GenericProcessor.cpp] ↓ GenericProcessor (juce::AudioProcessor) ↓ prepareToPlay → Core->Init processBlock → copy host buffer → Inputs[][] → Core->Calc(setup) → copy Outputs[][] → host buffer ↓ DAW hears processed audio

What lives on an AudioModule instance

  • Inputs / Outputs — float** planar buffers, length BlockLength
  • SampleRate, NumInputs, NumOutputs, Mode, Format
  • Specific — private state (e.g. GainSetup*)
  • Core — pointer to static AudioModuleCore (vtable of Init/Calc/Free/…)

The two symbols every *Plugin.h must provide

static const AudioModuleCore* amCore = &Gain;   // which C module
static const int ioConfigs[][2] = {
  { 8, 8 }, { 2, 2 }, { 1, 1 }               // channel layouts
};

createPluginFilter() reads these (via the per-plugin config header) and constructs GenericProcessor.

Reference modules to study (read-only)

  • Gain — simplest static gain DSP + VST3 folder
  • Template — official copy-source for new modules (scaffolding; not in product library by default)
  • Volume — gain + ramp parameters, meters, buttons (richer ParamInfo)
  • Clipper / SoftMute — still simple, different DSP shapes

Official new-module checklist

From Documents/AudioFramework.md:

  1. Create plugin from Modules\Template
  2. Add to Modules\VST3Plugins.sln
  3. Add to Framework\AudioLibrary.h/.c
  4. Add to Win64 / CSL_AFW / HiFi4 builds as needed
  5. Add to installer NSIS
  6. Docs generator + refresh AudioModules.xml + rebuild Tuning
Learning shortcut For your first learning VST, you can build a standalone module solution without completing every product-registration step. You still must understand the full checklist before Part 2 / shipping.

Architecture summary (memorize this)

AudioModuleCore = static "class" (function pointers + type name) AudioModule = one instance (buffers + Specific state) GenericProcessor = JUCE AudioProcessor wrapping one AudioModule GenericEditor = UI built from ParamInfo metadata createPluginFilter= factory the host calls on load
