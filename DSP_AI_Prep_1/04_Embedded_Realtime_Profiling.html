Turn “make it fast” into an engineering method

1. Real-time embedded thinking

For a periodic workload with period T, the critical question is whether the worst-case execution time and scheduling overhead fit within the deadline. Average execution time is not enough when missed deadlines are unacceptable.

Exercise 4.1

A block processes 128 samples at 48 kHz. What is the block period? If processing takes 2 ms, is it inside the nominal deadline?

128/48000 s = 2.6667 ms. A 2 ms processing time fits the nominal 2.667 ms budget, leaving about 0.667 ms before the next block deadline. In real systems you still need margin for jitter, interrupts, DMA, scheduling, and other workloads.

2. Profiling workflow / תהליך פרופיילינג

  1. Define the metric: cycles, wall time, CPU utilization, memory bandwidth, power, latency, or deadline misses.
  2. Create a reproducible baseline.
  3. Profile the workload.
  4. Locate the hottest or most constrained region.
  5. Classify the bottleneck: compute, memory, branch/control, synchronization, I/O, or numerical.
  6. Form one optimization hypothesis.
  7. Change the implementation.
  8. Run correctness tests.
  9. Benchmark again on the target-like environment.
  10. Keep or revert based on evidence.

Exercise 4.2

Your code is 20% faster after an optimization, but output error increased beyond the allowed tolerance. What do you do?

Reject the change as-is. First determine whether the numerical change is expected (e.g., reassociation/SIMD/fixed-point) and whether the tolerance or algorithm is wrong. If the product specification requires the original accuracy, optimize elsewhere or redesign the numerical method. Performance without required correctness is not a successful optimization.

3. Testing strategy

  • Unit tests for kernels.
  • Boundary tests: n=0, n=1, maximum sizes, alignment/tail cases.
  • Numerical reference comparisons with tolerances.
  • Randomized/property tests.
  • Stress tests.
  • Performance regression tests.
  • Target-hardware validation.

Exercise 4.3

List five bugs that a vectorized FIR implementation might introduce.

  • Wrong tail handling when n is not a multiple of vector width.
  • Out-of-bounds loads.
  • Incorrect coefficient/input alignment.
  • Accumulator/reduction mistakes.
  • Different rounding/precision behavior.
  • Aliasing assumptions that are not valid.
  • Incorrect stride or pointer increments.

4. Memory and power

Exercise 4.4

Why can reducing memory traffic improve both performance and power?

Moving data costs time and energy. If a processor spends cycles waiting for memory or repeatedly fetches the same data, reducing traffic can increase throughput and reduce energy spent on data movement. The exact result depends on the architecture and workload, so profile it.
