1. Why store configuration in JSON?

Programs often need values that change between machines, environments, or experiments: API URLs, file locations, model hyperparameters, feature flags. Hard-coding those inside Python makes every change a code edit and a redeploy. Putting them in a data file (here, JSON) lets you:

  • Edit settings without touching program logic.
  • Keep different files for dev, staging, and production.
  • Share the same code with different configs.
  • Version-control config separately (sometimes with different access rules).

JSON is a common choice because it is human-readable, widely supported, and maps cleanly to Python dicts and lists.

2. JSON syntax and Python’s mapping

JSON (JavaScript Object Notation) describes structured data as text. A minimal config might look like this:

{
  "app_name": "MyTool",
  "max_retries": 3,
  "enabled_features": ["export", "preview"],
  "database": {
    "host": "localhost",
    "port": 5432
  }
}

Rules that matter in practice:

  • Keys must be double-quoted strings.
  • Strings use double quotes, not single quotes.
  • Numbers, booleans (true/false), and null are literal; note JSON uses lowercase (Python uses None after parsing).
  • No trailing commas after the last item in an object or array.

After loading in Python, you typically get a dict at the top level:

config["app_name"]           # str
config["max_retries"]        # int
config["enabled_features"]   # list
config["database"]["host"]   # nested dict access

3. Files, paths, and the working directory

To read a JSON file, the program must know where on disk the file lives. That location is a path: either absolute (from the root of the drive) or relative (from some reference point).

Absolute path (Windows example):

C:\Users\you\project\config\settings.json

Relative path (depends on “current working directory” when the program runs):

config/settings.json

If you start Python from C:\Users\you\project, then config/settings.json resolves to C:\Users\you\project\config\settings.json. If you start from elsewhere, the same relative string may point to a different place or nowhere at all. That is why mature projects often build paths relative to known anchors (the project root, the file containing the script, or an environment variable) instead of assuming the working directory.

Takeaway: “Path string” + “how you resolve it” = which bytes actually get read. CNF_PATH-style variables are just a clear name for “the path we decided means our config file.”

4. The CNF_PATH pattern (and similar names)

You will see names like CNF_PATH, CONFIG_PATH, SETTINGS_FILE, or cfg_path. They are not magic: they are ordinary Python variables (often constants, written in UPPER_SNAKE_CASE) that hold a str or a pathlib.Path pointing at your JSON file.

Example A — fixed relative path (simplest):

CNF_PATH = "config/app_config.json"

Example B — path next to this source file (robust when cwd changes):

from pathlib import Path

HERE = Path(__file__).resolve().parent
CNF_PATH = HERE / "defaults.json"

Example C — project root + subfolder (common in apps):

from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]  # adjust depth as needed
CNF_PATH = ROOT / "config" / "production.json"

Example D — environment variable override (deployments):

import os
from pathlib import Path

CNF_PATH = Path(os.environ.get("APP_CONFIG", "config/default.json"))

The “resolves something” step you observed is usually: start from a known location (__file__, cwd, or env), combine path segments, maybe .resolve() to normalize .. and symlinks, and assign the result to CNF_PATH.

5. json.load vs json.loads

The standard library module is import json.

  • json.load(file_object) reads from an open text file and parses one JSON document. Use this when your JSON lives on disk (or any stream).
  • json.loads(string) parses JSON from a Python string already in memory (e.g. HTTP response body, or text you built in code).
import json
from pathlib import Path

CNF_PATH = Path("config/app_config.json")

with CNF_PATH.open(encoding="utf-8") as f:
    config = json.load(f)

print(config.get("app_name", "unnamed"))

Using encoding="utf-8" avoids surprises on Windows when the file contains non-ASCII characters. The with statement ensures the file is closed after reading.

6. End-to-end: resolve path → open → parse

Typical flow in three sentences: (1) Compute where the config file is and store that in something like CNF_PATH. (2) Open that path for reading as text. (3) Pass the open file object to json.load to get a Python dict (or list, depending on the file’s top-level structure).

import json
from pathlib import Path

def load_config(cnf_path: Path) -> dict:
    if not cnf_path.is_file():
        raise FileNotFoundError(f"No config at: {cnf_path}")
    with cnf_path.open(encoding="utf-8") as f:
        return json.load(f)

ROOT = Path(__file__).resolve().parent
CNF_PATH = ROOT / "settings.json"
settings = load_config(CNF_PATH)

After this, settings is a normal Python structure; the rest of the program reads keys, supplies defaults with .get(), or validates with a schema library if the project requires it.

7. Pitfalls and good practices

IssueWhat happensMitigation
Wrong cwdRelative path points to the wrong file or missing file.Anchor paths with Path(__file__), env vars, or documented project root.
Invalid JSONjson.JSONDecodeError at load time.Edit file carefully; use a JSON-aware editor; validate in CI.
Trailing commaInvalid in strict JSON.Remove trailing commas; or use JSON5 only if the project explicitly supports it.
Comments in fileStandard json module does not allow // or #.Use a format that supports comments (YAML, TOML) or strip comments in a documented way.
Huge integers / floatsPrecision or overflow surprises.Store big numbers as strings if exactness matters.

8. Exercises (work through in order)

Use a small scratch folder for these. Create real files and run the code yourself.

Exercise 1 — Create and load your first config

Create my_config.json with keys "title" (string) and "count" (integer). Write a script that sets CNF_PATH to that file, opens it, calls json.load, and prints both values.

Goal: Muscle memory for open + json.load.

Exercise 2 — Nested access

Extend JSON with a nested object "server": {"host": "127.0.0.1", "port": 8080}. Load it and build a URL string http://host:port/ from the dict (convert port to str when concatenating).

Goal: Comfortable navigation of nested dicts produced by JSON.

Exercise 3 — Relative vs anchored path

Write two scripts in different subfolders that both need the same shared/config.json. Make one script use a path relative to cwd (and observe failure when cwd changes). Refactor the second to use Path(__file__) so it always finds the file.

Goal: Understand why projects anchor CNF_PATH to __file__ or project root.

Exercise 4 — Missing file and bad JSON

Deliberately point CNF_PATH at a non-existent path; catch FileNotFoundError. Then corrupt the JSON (add a trailing comma) and catch json.JSONDecodeError. Print user-friendly messages.

Goal: Know the common exceptions and where they arise.

Exercise 5 — Environment override

Support reading MYAPP_CONFIG from the environment; if unset, fall back to default.json. Verify by setting the variable in your shell and printing which file was loaded.

Goal: Match deployment patterns where ops injects config location.

Exercise 6 — json.loads vs json.load

Read the same JSON content twice: once from disk with json.load, once by reading f.read() into a string and using json.loads. Assert the two resulting dicts are equal.

Goal: Clear mental model of stream parsing vs string parsing.

Exercise 7 — Small refactor into a function

Write load_json_config(path: Path) -> dict that checks existence, uses UTF-8, and returns the parsed object. Import it from a second module and load config from two different JSON files in one run.

Goal: Reusable pattern matching real project structure.

You are “expert enough” here when you can trace any CNF_PATH in a codebase to its anchor, predict the resolved absolute path, and load or debug JSON failures without guesswork.
