Python Packages and __init__.py

Audience: You can run Python files but are unsure why folders in projects contain __init__.py and what those files do. This guide explains namespaces, packages, imports, and the modern rules so you can read and design project layout like an experienced Python developer.

1. Modules: one file, one namespace

A Python module is typically a single .py file. When you import mymodule, Python executes mymodule.py (once) and binds names (functions, classes, variables) into a module object you access as mymodule.something.

The module’s file location on disk determines how it is found (via sys.path, the list of directories Python searches). You do not need __init__.py for a lone file on the path; you need correct path layout for imports to resolve.

2. Packages: directories of modules

A package is a way to group related modules under a common name so you can write hierarchical imports:

import mypkg.core
from mypkg.utils import helper

Here mypkg is the top-level package. On disk you usually have a directory:

mypkg/
  __init__.py
  core.py
  utils.py

Each .py file inside (that is meant to be imported) is a submodule. Subdirectories can be subpackages the same way, forming a tree.

3. What __init__.py is for

__init__.py is a regular Python file with a special name. When Python imports a package directory, it executes __init__.py for that package (if present and relevant to the import mode). That gives you a hook to control what the package name means to outsiders.

Roles it often plays:

  • Mark a directory as a package (classic / “regular” packages). Historically, an empty __init__.py was enough to tell Python “this folder is a package.” Many teams still keep the file for clarity and tooling even when it could be omitted in some setups.
  • Re-export a clean public API. You can import submodules inside __init__.py and expose names at the package level so users write from mypkg import foo instead of drilling into internal paths.
  • Run package-level setup. Rarely heavy work; more often registering plugins, setting __version__, or configuring subpackages. Avoid slow side effects on import unless the project clearly intends it.
  • Document intent. A short docstring at the top of __init__.py describes the package for help(mypkg) and for readers browsing the repo.

Example — minimal package surface:

# mypkg/__init__.py
"""Public API for mypkg."""

from mypkg.core import main as run
from mypkg import __version__

__all__ = ["run", "__version__"]

__all__ documents which names are intended when someone writes from mypkg import * (discouraged in application code, but still a useful signal).

4. Namespace packages (when __init__.py is optional)

Python 3.3+ supports namespace packages (PEP 420): certain directory layouts without __init__.py can still participate in imports when combined with other path entries. Libraries that split code across multiple install locations use this.

Practical rule: For your own application and most internal libraries, using __init__.py in each package directory remains the clearest, most compatible choice. Omitting it is a deliberate packaging decision, not a default shortcut for beginners.

The leading dot in from .module_a import ... means “relative to this same package”; see the next section.

6. Relative imports inside packages

Inside package code, sibling modules are often imported with relative syntax:

# inside mypkg/core.py
from .utils import helper      # mypkg.utils
from ..otherpkg import x       # parent of mypkg (only valid in a package)

Relative imports only work for modules loaded as part of a package; running a file directly as a script can break deep relative imports depending on how it is launched. That is a frequent source of ImportError: attempted relative import beyond top-level package when structure and launch method disagree.

7. Pitfalls and mental models

  • Circular imports: Package A imports B, B imports A during initialization. Sometimes solvable by local imports inside functions or restructuring layers.
  • Heavy work in __init__.py: Every import mypkg pays that cost. Keep package init lightweight unless designed otherwise.
  • Confusing public API: Re-exporting too much from __init__.py hides where code lives; balance convenience with discoverability.
  • Scripts vs packages: Running python mypkg/foo.py may not set up package context the same as python -m mypkg.foo. Prefer -m for package-internal modules when the project documents that workflow.

8. Exercises (work through in order)

Create a throwaway folder (not necessarily inside a large production repo) so you can experiment freely.

Exercise 1 — Smallest package

Create demo_pkg/__init__.py (can be empty) and demo_pkg/hello.py with a function say() that returns a string. From a sibling script at the project root, add the root to path if needed (or run with PYTHONPATH) and execute from demo_pkg.hello import say; print(say()).

Goal: See how a directory becomes importable as a package.

Exercise 2 — Package docstring

Add a module-level docstring to demo_pkg/__init__.py describing the package. In a REPL, import demo_pkg then help(demo_pkg) or demo_pkg.__doc__.

Goal: Connect __init__.py to the object bound to the package name.

Exercise 3 — Re-export API

In __init__.py, import say from hello and list it in __all__. Confirm from demo_pkg import say works.

Goal: Practice the barrel-export pattern used in many real libraries.

Exercise 4 — Nested subpackage

Add demo_pkg/tools/__init__.py and demo_pkg/tools/mathish.py with one function. Import it as from demo_pkg.tools.mathish import ....

Goal: Internalize multi-level package trees.

Exercise 5 — Relative import

Inside demo_pkg/tools/mathish.py, import something from demo_pkg/hello.py using a relative import (e.g. from ..hello import say). Call it from a function.

Goal: Read and write dotted relative imports without copying path strings.

Exercise 6 — python -m vs direct script

Add demo_pkg/main.py that imports from the package using relative or absolute imports as appropriate. Run it as python -m demo_pkg.main from the parent directory. Compare with python demo_pkg/main.py and note any import errors; adjust until you understand why.

Goal: Expert-level comfort with how Python sets __package__ and sys.path for each launch style.

Exercise 7 — Controlled side effect

In __init__.py, set demo_pkg.__version__ = "0.0.1" and print a one-line log only when an environment variable DEMO_PKG_DEBUG is set. Verify import behavior with and without the variable.

Goal: Learn to use package init deliberately instead of accidentally running expensive code on every import.

You are “expert enough” when you can open any repo tree, predict import paths from layout and __init__.py contents, choose between absolute and relative imports consciously, and debug import and circular-dependency issues without random shuffling of files.
