A. Computers do not store every real number

In pure math, numbers like 0.1 and 1/3 are exact ideas.

In a computer, a float / double can only store a finite number of bits. So most real values are stored as the nearest representable number — a tiny lie, called rounding.

Think of a ruler that only has marks every millimeter: a length of 2.37 mm might be recorded as 2 mm or 2 mm “plus a note you forgot.”

Floating-point arithmetic ≈ exact math, then round to nearest allowed value.

עברית

במתמטיקה מספרים יכולים להיות מדויקים לחלוטין. במחשב ל־float/double יש מספר סופי של ביטים, ולכן רוב הערכים נשמרים בתור הקירוב הקרוב ביותר שמותר לייצג. זה נקרא עיגול (rounding). אפשר לדמיין סרגל שמסומן רק כל מילימטר — אורך של 2.37 מ״מ ייכתב כ־2 או 3, ולא “באמת” 2.37.

B. Adding two floats can lose information

When you compute big + tiny, the result must fit in the same limited format.

If big is huge compared to tiny, the sum may round back to big. The tiny contribution is swallowed.

Example idea (toy decimals with only 4 significant digits): 1000 + 0.4 → stored as 1000 (the 0.4 vanished)

Real double has about 15–16 decimal digits of precision — same idea, just with more digits.

עברית

כשמוסיפים מספר גדול ומספר קטן מאוד, התוצאה חייבת להישאר באותו פורמט מוגבל. אם הפער גדול מדי, העיגול מחזיר את המספר הגדול — והתרומה הקטנה נעלמת. ב־double יש בערך 15–16 ספרות משמעותיות; העיקרון זהה.

C. Why long sums are dangerous in DSP

DSP kernels often compute things like:

  • signal energy: sum x[i]*x[i]
  • dot products / correlations
  • residual energy after subtracting a template

You add many terms into one running total. Early on the total is small; later it is large. Late tiny terms (or even moderate ones) can be rounded away. Your energy looks “almost right” but is systematically biased.

עברית

ב־DSP מחשבים הרבה פעמים אנרגיה, מכפלה פנימית, או אנרגיית שארית — כלומר סכום ארוך של איברים. בהתחלה הסכום קטן; בהמשך הוא גדול. איברים מאוחרים קטנים עלולים להיעלם בעיגול, והתוצאה נראית “בערך נכונה” אבל עם שגיאה שיטתית.

D. The idea of compensation (before the formula)

Naive sum: keep one variable s, do s = s + x[i] forever.

Compensated idea: also keep a second variable that remembers “how much we lost last time,” and feed that lost piece back into the next addition.

Like a cashier who notices the register rounded down 0.4 last sale, and adds that 0.4 into the next sale’s correction.

William Kahan published a simple, famous algorithm for this (1960s). It is cheap (a few extra flops per term) and widely used.

עברית

סכימה נאיבית: משתנה אחד s, ובכל פעם s = s + x[i].

רעיון פיצוי: שומרים גם משתנה שני שזוכר “כמה איבדנו בפעם הקודמת”, ומחזירים את האובדן לתוך החיבור הבא. כמו קופאי שמבחין שהמערכת עיגלה כלפי מטה ב־0.4 ברכישה הקודמת, ומתקן בזה בפעם הבאה. אלגוריתם קאהן הוא המימוש הקלאסי והזול של הרעיון הזה.

E. The Kahan algorithm (core)

Inputs: array x[0..n-1]. Outputs: compensated sum.

sum = 0 c = 0 // running compensation (lost low-order bits) for each x_i: y = x_i - c // apply previous compensation t = sum + y // tentative new sum (may round) c = (t - sum) - y // what got lost in (sum + y) sum = t return sum

Meaning of c: after adding y into sum, floating-point may not have kept all of y. The expression (t - sum) - y estimates the rounding leftover (with a sign convention so the next step subtracts it correctly via y = x_i - c).

Important: compilers that re-associate floating expressions aggressively can break Kahan. In practice, write the steps as separate statements; avoid flags that enable unsafe FP reassociation when validating.

עברית

אלגוריתם קאהן שומר שני משתנים: sum (הסכום) ו־c (פיצוי רץ).

בכל איבר: מתקנים את האיבר בעזרת c, מחברים ל־sum, ואז מחשבים מחדש כמה “נשפך” בעיגול — זה הופך ל־c של הצעד הבא. כך האובדן הקטן לא נזרק לנצח, אלא מנסים להחזירו בהמשך.

חשוב לכתוב את השלבים בנפרד; אופטימיזציות שמסדרות מחדש ביטויי נקודה צפה עלולות להרוס את הפיצוי.

F. What Kahan is (and is not)

Kahan isKahan is not
A way to reduce accumulation error in long sums A magic fix for every floating-point bug
Useful for energy, dots, residual norms in DSP A replacement for higher precision when you truly need it (long double, big-float)
O(n) time, small constant overhead Exact arithmetic on decimal values like 0.1

עברית

קאהן משפר סכימה ארוכה; הוא לא פותר כל בעיה בנקודה צפה, ולא הופך את החישוב למתמטיקה מדויקת לחלוטין. לצרכים קיצוניים לפעמים צריך דיוק גבוה יותר. לרוב אנרגיות/מכפלות ב־DSP — קאהן הוא כלי מצוין וזול.

Significant digits and swallowed additions

Theory

With a toy format that keeps only 3 significant decimal digits, any result is rounded to 3 digits. Adding a number smaller than the unit in the last place of a large sum can leave the sum unchanged.

Foundation · Ex 2
Naive running sum

Theory

A naive sum is one accumulator updated in order. Order matters in floating point: summing tiny values first, then a large one, often preserves more than summing large first.

עברית

סכום נאיבי = מצבר אחד שמתעדכן לפי הסדר. בנקודה צפה הסדר חשוב: קטנים קודם ואז גדול לעיתים שומר יותר מידע מאשר גדול קודם.

Handwriting

With 4 significant digits, compare:

  • Path A: ((0.001 + 0.001) + 0.001) + 1000
  • Path B: (((1000 + 0.001) + 0.001) + 0.001)

Which path keeps more of the small terms? (Approximate by rounding to 4 sig digits after every +.)

עברית — כתב יד

עם 4 ספרות משמעותיות, השווה מסלול שמתחיל בקטנים מול מסלול שמתחיל ב־1000. מי שומר יותר מהאיברים הקטנים?

Coding

  • Implement double sum_naive(const double *x, int n).
  • Test on {1e-8, 1e-8, ..., 1e-8} (one million times if practical, or 10000) plus nothing else — print sum and compare to n * 1e-8.
Path A builds ~0.003 then +1000 → about 1000 (small terms may still be lost at the last step depending on digit model).
Path B: each +0.001 into 1000 is often lost immediately with 4 digits → stays 1000.
Idea: large-first destroys tiny contributions sooner.
בדרך כלל התחלה עם המספר הגדול בולעת את הקטנים מוקדם יותר.

    return 0;
}
Building · Ex 3
Track the lost piece by hand (toy)

Theory

After a rounded add t = fl(sum + y), the true mathematical sum was sum + y. The difference between what you wanted and what you got is the rounding error of that step. Kahan estimates that error with (t - sum) - y (careful order).

עברית

אחרי חיבור מעוגל, ההפרש בין מה שרצינו למה שנשמר הוא שגיאת העיגול של אותו צעד. קאהן מעריך אותה בביטוי (t - sum) - y (הסדר חשוב).

Handwriting

Toy 4-digit arithmetic. Suppose sum = 1000, y = 1.234, and t = fl(sum+y) = 1001 (imagine low digits dropped).

  1. What is the exact sum + y?
  2. Compute (t - sum) - y with the toy numbers as if those operations were exact on the written values.
  3. Interpret the sign: does c say we overshot or undershot?

עברית — כתב יד

עם sum=1000, y=1.234, t=1001: חשב sum+y המדויק, את (t-sum)-y, ופרש אם פישלנו כלפי מעלה או מטה.

Coding

  • Write a function that, given sum and y, computes t, then c = (t - sum) - y, prints all three.
  • Try sum=1.0, y=1e-16.
Exact sum+y = 1001.234. t-sum = 1. Then (t-sum)-y = 1 - 1.234 = -0.234.
Negative c means the next step will add a bit back via y = x - c.
הסכום המדויק 1001.234; c≈-0.234 אומר שאיבדנו חלק חיובי מהתוספת.

    double y = 1e-16;
    double t = sum + y;
    double c = (t - sum) - y;
    printf("t=%.17g c=%.17g\n", t, c);
    return 0;
}

עברית — כתב יד

Coding

  • Implement double sum_kahan(const double *x, int n).
  • Compare sum_naive vs sum_kahan on one large value followed by many tiny ones, e.g. x[0]=1.0 and x[i]=1e-16 for i=1..N.
  • Print both sums and the “mathematical intention” 1.0 + N*1e-16 (knowing double may not represent that exactly either).

#include <stdio.h>

double sum_kahan(const double *x, int n)
{
    double sum = 0.0;
    double c = 0.0;
    for (int i = 0; i < n; ++i) {
        double y = x[i] - c;
        double t = sum + y;
        c = (t - sum) - y;
        sum = t;
    }
    return sum;
}

double sum_naive(const double *x, int n)
{
    double s = 0.0;
    for (int i = 0; i < n; ++i) s += x[i];
    return s;
}

int main(void)
{
    enum { N = 100 };
    double x[N];
    x[0] = 1.0;
    for (int i = 1; i < N; ++i) x[i] = 1e-16;
    printf("naive=%.17g\n", sum_naive(x, N));
    printf("kahan=%.17g\n", sum_kahan(x, N));
    printf("wish =%.17g\n", 1.0 + (N - 1) * 1e-16);
    return 0;
}
Intermediate · Ex 5
Kahan for sum of squares (energy)

Theory

Energy E = Σ x[i]² is a sum — so Kahan applies to the squared terms, not by “Kahan inside the multiply.” You still compute term = x[i]*x[i] normally, then compensate-add term into the accumulator.

עברית

אנרגיה היא סכום של ריבועים. קאהן פועל על איברי הסכום (הריבועים), לא על הכפל עצמו: מחשבים term = x[i]*x[i] ואז מחברים את term בשיטת קאהן.

Handwriting

Write the Kahan loop where the input to each step is x[i]*x[i] instead of x[i]. Box the line that changes.

עברית — כתב יד

כתוב את לולאת קאהן כשהקלט בכל צעד הוא x[i]*x[i]. סמן איזו שורה השתנתה.

Coding

  • Implement double energy_kahan(const double *x, int n).
  • Also implement naive energy.
  • Test on a vector with one large sample and many small ones.
Only the formation of the addend changes: y = (x[i]*x[i]) - c; then same t/c/sum updates.
רק יצירת האיבר המחובר משתנה לריבוע; שאר עדכוני קאהן זהים. 
#include <stdio.h>

double energy_kahan(const double *x, int n)
{
    double sum = 0.0, c = 0.0;
    for (int i = 0; i < n; ++i) {
        double term = x[i] * x[i];
        double y = term - c;
        double t = sum + y;
        c = (t - sum) - y;
        sum = t;
    }
    return sum;
}

int main(void)
{
    double x[5] = {10.0, 1e-8, 1e-8, 1e-8, 1e-8};
    printf("E=%.17g\n", energy_kahan(x, 5));
    return 0;
}

Advanced · Ex 7
Neumaier’s improvement (optional hero tier)

Theory

Classic Kahan can stumble if a single |x_i| is larger than the current |sum| (the roles of “big” and “small” flip). Neumaier summation is a common variant: it chooses which value is larger before forming the compensation, so large new terms are handled more safely. You do not need Neumaier for the DSP workbook exercise, but heroes know it exists.

עברית

קאהן הקלאסי עלול להיחלש אם איבר חדש גדול מהסכום הנוכחי (מי “גדול” ומי “קטן” מתהפך). סכימת נוימאייר היא וריאציה שבוחרת לפי הגודל לפני חישוב הפיצוי. לא חובה לתרגיל ה־DSP, אבל כדאי להכיר.

Handwriting

In one sentence: when would you prefer Neumaier over classic Kahan?

עברית — כתב יד

במשפט אחד: מתי תעדיף נוימאייר על פני קאהן הקלאסי?

Coding

  • Implement double sum_neumaier(const double *x, int n) from a reference description you trust (or the sketch below in the reveal).
  • Compare naive / Kahan / Neumaier on a sequence that starts tiny and ends with a huge spike.
Prefer Neumaier when individual terms can exceed the running sum in magnitude (unsorted / spiky data).
כשיש איברים בודדים שיכולים לגדול מהסכום הרץ (נתונים עם קפיצות). 
#include <math.h>
#include <stdio.h>

double sum_neumaier(const double *x, int n)
{
    double sum = 0.0;
    double c = 0.0;
    for (int i = 0; i < n; ++i) {
        double t = sum + x[i];
        if (fabs(sum) >= fabs(x[i]))
            c += (sum - t) + x[i];
        else
            c += (x[i] - t) + sum;
        sum = t;
    }
    return sum + c;
}

int main(void)
{
    double x[4] = {1e-16, 1e-16, 1e-16, 1.0};
    printf("%.17g\n", sum_neumaier(x, 4));
    return 0;
}

המקום החשוב ביותר לקאהן הוא סכום הריבועים של השארית; גם המכפלות הפנימיות עוזרות כש־n גדול. 
#include <stdio.h>

static double sum_kahan(const double *x, int n)
{
    double sum = 0.0, c = 0.0;
    for (int i = 0; i < n; ++i) {
        double y = x[i] - c;
        double t = sum + y;
        c = (t - sum) - y;
        sum = t;
    }
    return sum;
}

void process_residual(const double *t, const double *x, int n,
                      double *r, double *g_out, double *energy_out)
{
    double tt = 0.0, tx = 0.0, c1 = 0.0, c2 = 0.0;
    for (int i = 0; i < n; ++i) {
        double y1 = t[i] * t[i] - c1;
        double s1 = tt + y1;
        c1 = (s1 - tt) - y1;
        tt = s1;

        double y2 = t[i] * x[i] - c2;
        double s2 = tx + y2;
        c2 = (s2 - tx) - y2;
        tx = s2;
    }
    double g = (tt == 0.0) ? 0.0 : (tx / tt);
    for (int i = 0; i < n; ++i) r[i] = x[i] - g * t[i];

    double energy = 0.0, c = 0.0;
    for (int i = 0; i < n; ++i) {
        double term = r[i] * r[i];
        double y = term - c;
        double s = energy + y;
        c = (s - energy) - y;
        energy = s;
    }
    *g_out = g;
    *energy_out = energy;
    (void)sum_kahan; /* available if you prefer a helper on a temp buffer */
}

int main(void)
{
    double t[8] = {1,1,1,1,0,0,0,0};
    double x[8] = {2,2,2,2,1,1,1,1};
    double r[8], g, E;
    process_residual(t, x, 8, r, &g, &E);
    printf("g=%.6f E=%.6f\n", g, E);
    for (int i = 0; i < 8; ++i) printf("%.4f ", r[i]);
    putchar('\n');
    return 0;
}
